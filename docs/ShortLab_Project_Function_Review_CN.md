# short-lab 项目功能、策略逻辑与代码审查

审查日期：2026-10-08  
代码基线：`edd81adcc2cc1436c33f86db1b2d5a8bd21e3ad5`（分支 `short-meme`）  
范围：当前桌面端的实际代码、默认配置、数据链、后台任务、API、前端和证据评估。Android 不在本次范围内。

## 1. 结论

**当前项目具有做空候选筛选、资金费分析、手工对冲规划和头寸监控的基础，但尚不能完整、可靠地达成“找出适合做空的 Meme 合约，并正确判断是否需要现货对冲”的目标。**

主要原因有三类：

1. 默认生产链存在数据与接线缺口，身份目录、行情来源时间、Funding 存量来源时间等未完整传递。纯计算函数可以通过测试，正常启动后的候选评分却可能缺失或使用错误的风险输入。
2. 对冲规划有关键判断错误：当前资金费转负仍可显示 READY；强平价与 STOP 指导混用价格单位；持有期限未进入经济门槛；未知止损能力被提升为已验证。监控前端还存在旧计划数据与新计划写入目标混用的问题。
3. 系统没有独立的“是否对冲、对冲多少”决策层，也缺乏足够的样本外证据证明评分具有做空优势或部分对冲优于基线。当前对冲比例主要由用户选择或风险预算公式生成。

这些问题应分成“代码正确性修复”“完整业务流程建设”“策略有效性验证”处理。三者各自有验收要求，测试通过不能替代策略效果证明。

### 1.1 能力判断

| 用户目标 | 当前能力 | 判断 |
|---|---|---|
| 获取可交易合约、行情、资金费、OI、盘口及现货信息 | 有生产 Provider 和预算框架 | 已实现基础能力，来源时间和覆盖率链需修复；本次未验证实时网络可达性 |
| 区分 Meme 与普通币，建立合约和现货的同一资产关系 | 有目录、人工覆盖、Resolver | 默认调用链及倍率/置信度传递有缺口，不能认为全市场可靠识别 |
| 找出具有长期做空特征的候选币 | 有 LTSS、Profile、Entry、DQ、风险状态 | 能计算规则评分；生产接线与部分时间窗口有错误；评分尚未证明预测优势 |
| 入场前确保当前资金费为正 | 已有配置与历史统计 | 配置门槛未实际统一执行，可出现负费率 READY |
| 计算用户指定的 1:1 或部分对冲 | 有 Decimal 数量换算、合法化、成本和压力计算 | 基础可用，但强平单位、持有期、止损能力与舍入后预算需修复 |
| 自动判断是否应该对冲 | 未形成联合决策合同 | 未实现完整决策能力，FCS 和 Safety 均不能替代该判断 |
| 指导双边入场及平仓 | 有入场和合约保护单指导、孤腿风险告警 | 缺完整双边退出指导与连续使用流程 |
| 持仓期间及时展示风险与净收益 | 后台任务和监控计算存在 | 前端无自动刷新；实际 PnL、费用输入未完整接线 |
| 证明策略有效 | 有历史评分、Outcome、Grader、Metrics 框架 | 生产采样和指标接线存在缺口；本地没有足够策略样本 |
| 保证 1:1 对冲无损、只赚资金费 | 不具备此能力 | 该目标本身不能被保证；需明确基差、成本、强平及人工操作风险 |

### 2.1 实际业务链

```text
公开市场数据 → 身份解析 → 冻结输入 → LTSS/Profile
                                 → Entry/DQ/风险 → 做空候选

公开资金费/现货报价 → FCS → Funding 机会

用户选择模式/比例/预算 → 对冲模拟 → 保存计划
                     → 用户手工登记成交 → 监控/告警

历史快照/市场归档 → Outcome Grader → Evidence/Metrics
```

当前缺失的是做空候选和 Funding 机会之间的联合决策：

```text
候选 + Funding 入场条件 + 持有期限 + 风险预算 + 可执行报价
  → 应避免 / 信息不足 / 裸空 / 部分对冲 / 完全对冲
```

### 2.2 值得保留的机制

- 数据缺失可以返回 null/UNKNOWN；未知 FX、倍率和历史报价不应猜测补齐。
- LTSS 与 Entry 分离，候选状态与执行状态分离，长期特征和短期入场有不同职责。
- Decimal 账本、不可变手工事件、幂等和版本比较提供了正确基础。
- 历史 Entry 要求冻结输入；历史报价缺失不应使用当前报价回填。
- 强平事件需要用户确认；仅触及强平阈值不擅自清空仓位。合约已平而现货尚存可触发孤腿退出提醒。
- 项目保持只读公开数据与人工记账，不需要增加自动交易权限才能完成本次优化目标。

## 3. 策略逻辑的适用边界

### 3.1 LTSS、Entry、FCS 分别回答什么

- **LTSS**：资产具备多少设计所规定的长期做空特征。是加权规则分，不是下跌概率。
- **Entry**：技术共识、MTF、Micro、Regime、反弹失败、Funding 等是否支持当前方向性入场。不是未来收益保证。
- **FCS**：资金费捕获条件的规则排序。高 FCS 不能推出价格将下跌，也不能单独推出应当使用部分对冲。
- **DQ/Safety/READY**：应明确是数据、执行、经济性还是风险状态。当前部分代码把这些语义混用，需要拆分。

“高评分”与“几乎不可能翻倍”之间没有经过验证的概率关系。应删除此类推导，改为展示压力场景、数据置信度和可承受损失。

### 3.2 三种目标需要不同规则

| 目标 | 方向暴露 | 推荐逻辑的前提 |
|---|---|---|
| 主要赚资金费 | 接近中性，通常考虑完全对冲 | 当前及上次结算费率、持有期净收益、双边退出能力、保证金和成本通过门槛 |
| 主要赚做空下跌收益 | 保留负方向暴露 | 做空证据、入场条件、上行情景损失、强平距离、风险预算通过门槛 |
| 资金费与下跌收益兼顾 | 部分负方向暴露 | 两组条件同时满足，再寻找满足损失预算的可执行比例 |

在现货和合约同幅变动、初始基差忽略、无强平且数量正确的简化假设下：

`方向盈亏 ≈ (h − 1) × N × r`

其中 `h` 为现货数量/合约对应资产数量，`N` 为初始合约名义金额，`r` 为资产涨跌幅。`h=1` 抵消主要方向敞口；`h=0.5` 保留约一半做空敞口。实际净收益还需计入 Funding、基差、FX、手续费、滑点、Gas、数量舍入与单腿未成交。

正资金费时，多头向空头付费；负资金费时空头付费。资金费结算间隔可变化，不能一律按固定 8 小时认定完整历史。[Binance 资金费规则](https://www.binance.com/en/support/faq/detail/360033525031)

匹配的现货多头与合约空头可以降低方向暴露，但不能保证无损。合约保证金和维持保证金仍约束强平；持有另一处现货并不自动增加该合约账户的保证金。手工在强平后卖出现货存在时差和价格风险。[Binance 资金费套利说明](https://www.binance.com/en-AE/support/faq/detail/61012e690cf343e7979649282a2ccc3c)、[强平规则](https://www.binance.com/en-NG/support/faq/detail/360033525271)

## 4. 已确认问题与具体修复方案

优先级定义：P1 直接影响选币、经济性、风险判断、账本或告警可信度；P2 影响完整性、配置、操作效率或评估能力。以下代码路径以第 2 节包根为基准；UI 路径另写完整项目相对路径。

### 4.1 身份、数据与做空筛选

#### S01 · P1：身份目录未进入默认做空评分链

- **位置**：`shortlab/service.py:490、2110`；`shortlab/runtime.py:461–471`。
- **事实**：Runtime 传入 `identity_catalog`，默认 `_identity_candidates_fn` 仍返回空列表；评分只消费该函数。核验目录存在 BTC 候选，但默认 Service 候选函数输出为空。
- **影响**：人工覆盖以外的资产可能 UNRESOLVED，MC/ATH 无法使用，LTSS 不完整；目录刷新成功不代表评分获得目录。
- **修复**：统一身份入口，默认从已注入 Catalog 获取候选；保留显式测试注入。做空和 Hedge 都消费同一份解析后 IdentitySnapshot，不能直接选目录第一条当核验结果。
- **验收**：正常 Runtime 无额外注入时，普通资产和 Meme 均能消费目录；歧义资产继续 UNKNOWN；覆盖和目录冲突可解释。

#### S02 · P1：可信倍率与置信度在身份交接中丢失

- **位置**：`shortlab/identity/resolver.py:412、519`；`identity/catalog.py:304`；`service.py:3219`；`hedge/planner.py:590`。
- **事实**：Resolver 倍率主要取交易所元数据，未保留核验候选中的可信倍率。BTC 目录明确 `1/MANUAL`，解析结果仍可倍率 null。Hedge 的目录分支直接返回原始候选，核验文件不含 Planner 所读的置信度字段。
- **影响**：合法资产被拒绝，或同一资产在扫描和规划中身份信用不同。
- **修复**：定义解析后 DTO，明确倍率、来源、映射置信度及冲突优先级；只接受可追溯人工/交易所来源，不猜符号前缀；Hedge 不绕过 Resolver。
- **验收**：普通 1 倍与 1000 倍核验资产通过同一解析路径，倍率与置信度一致；矛盾或未知仍拒绝规划。

#### S03 · P1：行情行丢失来源时间，当前价退回日线，24h 突破暂停失效

- **位置**：`data/universe.py:326–339`；`shortlab/service.py:2698–2722`；`inputs.py:670`。
- **事实**：Universe 仅保留价格/涨幅/量，未保留来源与已知时间；冻结层将 Ticker 判为 `LEGACY_PROVENANCE_UNKNOWN`。离线复现：当前价 44.744、涨幅 40%，冻结后价变为日线收盘 31.96，24h 涨幅为 null，暂停未触发。
- **修复**：Provider 返回真实 DataObservation，保存交易所时间与首次接收时间；缓存命中保留原时间。缺风险输入应明确降级，不能把缺失当未触发。
- **验收**：生产采集→冻结→风险集成中，当前价来源可解释，+40% 正确触发暂停；过期/无来源时间不获得实时风险信用。

#### S04 · P1：完整 Funding 存量重读后失去来源时间

- **位置**：`shortlab/service.py:2343–2381`。
- **事实**：完整历史会跳过 HTTP，但已知时间依赖进程内 `_funding_known_at`。完整 30D 档案复现：网络请求 0 次、`fetched_at=None`，冻结 Funding30D 为 null。
- **修复**：在首次采集/回填时持久化接收时间和来源证明，重启从档案恢复；不得把数据库读取时间伪装为首次已知时间。旧数据缺证明需明确 Legacy/重新校验。
- **验收**：采集→停止→重启，无网络重取仍得到同一合法 Funding 输入；来源未知档案继续降级。

#### S05 · P1：7D 价格/OI 配对实际使用 8D OI 窗口

- **位置**：`shortlab/inputs.py:752–757`。
- **事实**：价格比较 7D 收盘点，OI 起点却采用更早日线开盘。复现 OI 窗口 8 天；真正对齐的 7D 输入被判 `WINDOW_MISALIGNED`。
- **修复**：以两端已收盘日线的比较时刻生成明确的 7D 窗口，OI 在同一端点取值；明确时间容差、禁止前视。
- **验收**：真实 7D 可用、8D 拒绝；UTC 边界和未收盘日线覆盖测试。

#### S06 · P1：Squeeze 暂停缺确认输入，生产链不能完整执行

- **位置**：`shortlab/service.py:1975、2195–2207、2850–2868`；`inputs.py:400–465`。
- **事实**：暂停需要价格/OI 上升及 Taker 或 Micro 确认，生产链未将完整确认输入交给风险模块。价格/OI 均 +20% 时缺确认不触发；添加 Micro/Taker 后触发。
- **修复**：在冻结 RiskInput 中显式保存 Taker、Micro 和来源时点；Entry 与风险共用对应快照，禁止事后从当前值补历史。
- **验收**：真实编排链触发/不触发两例；未知确认输入显示风险未验证，不能称已检查安全。

#### S07 · P2：人工 Profile 覆盖与类别稳定性不完整

- **位置**：`shortlab/service.py:2175`；`scoring/profiles.py:159–178`；`identity/overrides.py:31–44、99–101`。
- **事实**：选择器读取顶层 Profile，但 Service 传入按 symbol 嵌套的全表；覆盖校验也不接受对应键。已知 Meme 类别在 Fundamentals 缺失时可能转 GENERAL。
- **修复**：冻结按资产的覆盖合同，身份类别与数据质量分离；已确认 Meme 不因临时数据失败变为普通币。
- **验收**：人工 Profile 生效；Fundamentals 暂时失败仍保持类别、只降 DQ；分类变化带版本和原因。

#### S08 · P2：WATCH/CANDIDATE 配置未消费

- **位置**：`shortlab/risk/veto.py:640–645`；`service.py:2300–2313`。
- **事实**：分档硬编码 60/70；修改配置无法改变候选结果。
- **修复**：从冻结策略配置读取全部阈值，版本/hash 对应实际使用参数。
- **验收**：调低门槛的边界样本确实变更状态；非法顺序配置启动失败。

#### S09 · P2：原有共识严重冲突阈值不可达到

- **位置**：`engine/consensus/engine.py:60–65`；`consensus/risk.py:60–69`；`engine/config/default.yaml:11`。
- **事实**：少数方向/双边合计最大为 0.5，配置门槛为 0.6，严重冲突分支不可达。等权 3 个强卖与 3 个买可产生 SELL/置信度 34。
- **修复**：统一冲突量纲与有效阈值，极端双边分歧抑制方向输出；区分指标参与率、强度与一致性。
- **验收**：对称双边冲突、少数强反向、一致弱方向三类用例，Entry 不从严重冲突取得过高方向信用。

### 4.2 Funding 与对冲规划

#### H01 · P1：当前/上次资金费转负仍可能 READY

- **位置**：`shortlab/hedge/funding_score.py:948`；`hedge/planner.py:794、1033`；`config.py:1000、1004`。
- **事实**：已有 `entry_gate` 参数未统一执行。保持长期正资金费历史，只将当前和上次结算改为 -0.0005，复现 FCS=100/READY，Planner 仍 READY。
- **修复**：新增共用纯函数 `evaluate_funding_entry_gate`，机会与模拟都调用；消费当前、上次结算、7/30D、正值比例、覆盖率和来源新鲜度。历史高分仍可查看，但独立显示不可入场原因。
- **验收**：当前/上次结算正、零、负、未知交叉矩阵；双负高历史 APR 不得入场 READY；每个门槛配置改变实际结果。

#### H02 · P1：Funding 覆盖率忽略真实结算间隔

- **位置**：`hedge/funding_score.py:151`；`evidence/hedge_grader.py:1224`；`hedge/market.py:204、216`。
- **事实**：最大缺口不超过 24h 被视为完整；每天仅一笔的 95D 数据可得到覆盖率 1。如果真实间隔是 8h，实际缺失 2/3 事件。
- **修复**：归档 Funding 间隔及生效历史，按预期结算槽位检验；窗口首尾与中间缺口统一处理。未知间隔不授完整覆盖，合法变更分段计算。
- **验收**：8h 丢 2/3 不完整；8h→4h 合法变更不误判；覆盖率影响 FCS、入场门槛和 Grader。

#### H03 · P1：1000 倍合约强平/STOP 混用价格单位

- **位置**：`hedge/planner.py:875、876、997、1341、1346`；`service.py:3670`；`hedge/jobs.py:200`。
- **事实**：规划中将交易所原生强平价与 canonical USD 价比较。原生 mark=10、倍率=1000、强平=15 时，+50%/+100% 场景仍 OK，STOP=7.505，低于当前原生价；正确中点为 12.5。
- **修复**：请求中的强平和触发价统一为 instrument 原生 quote 单位；风险比较用 native/native，USD 仅用于报告。STOP 按原生 Tick 合法化并验证位置。
- **验收**：倍率 1/1000 × FX 1/0.97；上述场景强平后结果无效，STOP 正确且规划/监控一致。

#### H04 · P1：持有期限未参与经济性判断

- **位置**：`hedge/models.py:491`；`hedge/planner.py:520、794、812、1050`。
- **事实**：接受 `planned_hold_days`，计算不使用它。持有 1 天、保守 APR=2%、回本约 54.66 天的样本仍 READY。
- **修复**：按合法化后合约 Notional 计算目标期限保守资金费、完整往返成本和净 Carry；将执行可行与经济候选分开。部分对冲方向 PnL 单列，不掩盖负 Carry。
- **验收**：同输入 1/60 天经济结果不同；期限不足明确原因；成本或收益未知不授经济 READY。

#### H05 · P1：未知平台止损能力提升为已验证

- **位置**：`hedge/planner.py:1053、1064、1178–1193`；`hedge/venues/binance_spot.py:502`。
- **事实**：缺少 STOP 能力字段时结果可当作支持。只有 LIMIT/MARKET 的规则和用户选择 `USER_PLATFORM_ORDERS`，仍可得到 VERIFIED/FULL，指导本身又显示 LIMITED。
- **修复**：能力采用支持/不支持/未知三态；平台支持、用户选择、实际保护单确认分别保存。用户手工回执含腿、数量、触发基准与确认时间；确认超时或撤单后降级。
- **验收**：未知不可提升 VERIFIED；页面、模拟、指导能力一致；不把手工确认称为保证成交。

#### H06 · P1：舍入后风险预算和真实压力约束未完整校验

- **位置**：`hedge/planner.py:284–319` 及数量合法化/压力计算链。
- **事实**：`h=1−L/(N×u)` 依赖同涨幅、无强平、无基差/成本冲击；合法数量、扣币费率及实际腿金额可能改变风险暴露。
- **修复**：以最终合法数量重算基差、FX、双腿不同涨幅、跳空、保证金、退出折价和人工延迟情景；把数学下限与可执行比例分开。没有可行比例返回预算不满足。
- **验收**：Floor/Dust、最小单、不同币种计费边界；每个已声明场景满足预算或明确拒绝，不能靠 Safety 加权分抵消硬失败。

#### H07 · P2：FCS 数据齐全、执行可行和经济性语义混用

- **位置**：`hedge/funding_score.py:733、875、948`。
- **事实**：完整负费历史可 FCS=43/READY；不能交易等条件有的仅扣分。
- **修复**：分开 `data_complete`、`entry_eligible`、`execution_ready`、`economic_candidate`；非 TRADING、退市、身份未知、报价过期、退出不可行作为相应硬门槛。与 H01 共用合同。
- **验收**：完整负 Carry、非 TRADING、退市、STALE 不显示可执行资金费推荐；低分历史仍可只读查看。

#### H08 · P2：生产 Funding 投射缺 7D/最佳场所/回本期及一致历史类型

- **位置**：`hedge/jobs.py:259–283`；`service.py:3403–3435`；`hedge/funding_score.py:980–1010`。
- **事实**：API 缺 Funding7D；任务写 `venue`，API 读 `best_venue`；任务没产生回本期。上市年龄未统一传递，45 天资产可能误按 FULL_90D。FCS job 未传真实配置 hash。
- **修复**：冻结统一 FundingContext/Projection，保存 listingAge、historyClass、收益方法、最佳可用 Venue、成本、BE、来源时间与 hash；API/UI 消费同合同。
- **验收**：真实 worker→仓库→API→UI 离线集成；Venue 过滤不丢合法结果；45 天按 PARTIAL；非正收益的 BE 有明确不可回本语义。

### 4.5 默认能力及外部数据成本

- `shortlab/default.yaml` 中 Funding Capture 和 Hedge 默认关闭。这是明确的默认范围，不应称为后台已运行；界面应显示是否启用、Provider 是否配置、最近成功时间与能力限制。
- Alpha/链上默认能力受到配置和 PoC 限制。0x indicative Quote 不等于可执行买卖能力，不能为其授双边可退出信用。
- 全市场每小时逐币请求可能无法满足 CoinGecko 月配额。示例：500 币×24×30=36 万次/月；每分钟独立 FX 请求另约 4.32 万次/月。该数值是负载推演，非实测当前请求量。应按账户真实额度、批量接口、缓存和优先级测算。[CoinGecko API 配额](https://www.coingecko.com/en/api/pricing)
- Binance OI 历史接口的可查询范围有限，不能期待随时补出任意 90D OI；需要从启用日起持续归档，老资产没有历史就降级。[Binance USDⓈ-M 市场数据文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data)

## 5. 联合对冲决策层设计建议

### 5.1 合同和边界

建议新增 `shortlab/hedge/decision.py` 与明确的 Decision DTO；Service 负责编排，Planner 校验可执行数量，UI 展示证据和操作指导。

输入必须是版本化冻结上下文：

- IdentitySnapshot 与原生单位/倍率/Quote Currency。
- LTSS、Entry、DQ、BLOCK/PAUSE 和各组来源时间。
- 当前/上次结算 Funding、真实覆盖率、保守收益方法及历史类型。
- 完整双向 Quote、合法交易规则、当前 Mark、已知/未知成本与 FX。
- 用户目标：`CARRY_CAPTURE`、`DIRECTIONAL_SHORT`、`BALANCED`。
- 目标期限、资本、合约保证金/杠杆和原生强平价、可承受损失、手工操作约束。
- 明确列举的上行、下行、基差、FX、退出折价和操作延迟情景。

输出建议独立于现有候选/执行状态：

`DATA_INSUFFICIENT / MANUAL_REVIEW / AVOID / NO_HEDGE / PARTIAL_HEDGE / FULL_HEDGE`

每个输出含目标、输入引用、模型版本、理由、假设、风险硬门槛、建议合法数量、实际比例、预计 Carry/成本/期限净额、压力结果与有效期。

### 5.2 决策顺序

1. 核验资产、单位和数据时效；缺关键输入返回信息不足。
2. 检查不可交易、退市、风险暂停及用户要求的正资金费门槛；失败明确不建议入场。
3. 区分 Carry 与方向目标。Carry 不应因为 LTSS 低而自动排除真正中性的机会；方向目标不能仅依赖 FCS。
4. 从合法数量生成可执行比例候选，按实际成本、保证金和已声明情景校验风险预算。
5. 排除期限内净 Carry 不足的 Carry 方案；对方向方案分别展示方向损益和 Carry，不把下跌收益计为确定收益。
6. 在可行方案中按目标选择；没有可行方案返回 AVOID，不静默降低对冲比例或扩大风险预算。
7. 输出指导和到期条件；输入过期/费率反转/退出能力下降重新计算，不自动交易。

`max(0, 1−L/(N×u))` 只可作简化场景的比例下限，不可当最优比例或损失保证。最终采用合法化后数量计算。

`NO_HEDGE` 需要独立单腿方向计划或明确预期腿集合；当前两腿 Hedge 的孤腿检测不能把有意裸空误当异常，也不能为规避告警伪造现货成交。

## 7. 完成目标的验收标准

### 7.1 找到可研究的 Meme 做空候选

- 默认 Runtime 能核验普通/倍数合约与现货对应关系，Meme 类别稳定，歧义和缺数据可解释。
- 所有期限一致，风险输入真实且足够新；24h Breakout/Squeeze 不因缺字段静默失效。
- 页面区分研究候选、可入场、暂停和不可执行，不把规则分当下跌概率。
- 有足够、可追溯的真实 Forward 样本，按状态/模型版本分桶；未验证时明确标记。

### 7.2 判断现货对冲并给出手工指导

- 正 Funding 门槛实际生效，历史正收益不能覆盖当前负费率。
- 目标、期限、资本与风险预算决定建议；未知输入输出信息不足。
- 倍率、FX、强平和 Tick 单位正确；舍入后风险重新检验。
- 完整买入、保护、双边平仓指导均使用原生单位与剩余数量。
- 用户手工成交/部分平仓/强平/资金费入账后，账本、净收益与告警一致。
- 前端及时更新、失败标过期、不会跨计划混账。
- 完全对冲说明其残余风险；部分对冲展示剩余方向暴露；不承诺无损或不会翻倍。

### 7.3 验证推荐具有实际价值

- 比较裸空、固定比例和系统选择，使用相同时间/资产与完整成本。
- 单独报告净收益、尾部损失、强平/单腿风险、换手、成交可行性、覆盖率和删失。
- 无前视，缺历史可执行报价不能使用今日数据替代。
- 使用滚动样本外验证；通过代码测试与达到策略统计门槛是两项独立验收。
